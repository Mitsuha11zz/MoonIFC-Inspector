## 项目简介

MoonIFC Inspector 计划在 MoonBit 生态中提供一套可复用的 IFC（Industry Foundation Classes）模型解析、结构审计与关系查询引擎，为建筑、工程与施工（AEC）领域的模型查看器、模型质检工具、构件统计面板、Web 端轻量交付审查和低代码 BIM 编辑器提供底层能力。项目面向需要在 MoonBit 中处理建筑模型数据的库作者、工具开发者和应用开发者，提供 STEP 文本解析、领域实体建模、双向引用关系索引、可扩展审计规则调度以及 JSON、文本与引用列表三类报告输出。

IFC 是建筑行业事实上的开放数据交换标准，由 buildingSMART 以 ISO 16739 发布，绝大多数 BIM 软件（Revit、ArchiCAD、Tekla、Bentley 等）都能导出。它的物理载体是 STEP（ISO 10303-21）文本格式，一个 IFC 文件本质上是数万到数百万行带编号的实体记录，实体之间通过 `#编号` 互相引用，构成一张巨大的有向图。现实中这份数据脏得非常普遍——导出工具截断、构件库版本不一致、协同过程中删改了被引用的对象——都会导致悬空引用和 GlobalId 冲突，而这类问题在导入下游系统时才爆发，排查成本极高。

传统的处理方式依赖 IfcOpenShell（C++/Python）、xBIM（.NET）或 Web 端 ifc.js 等重量级方案，它们要么需要 Python 运行时与 C 扩展，要么依赖 JS 生态与庞大的几何内核，包体积和启动开销都很难接受，并且把"校验"和"渲染"这两件正交互补的事强行绑在一起。MoonIFC Inspector 的取舍是只做前者：剥离几何运算与三维渲染，专注 STEP 文本解析与结构一致性审计，从而得到一个零平台依赖、可编译到 wasm-gc 的纯解析内核，模型不必上传服务器即可在浏览器本地完成校验。

项目采用清晰的领域分层：`step_text` 负责无平台依赖的 STEP 文本扫描，`ifc_entities` 把记录转换为领域实体，`relation_map` 提供引用查询，`model_rules` 生成稳定排序的审计发现，`report_view` 负责 JSON、文本与引用列表输出。应用层只组合这些领域包，不把规则逻辑复制到 CLI 或浏览器层。这一约束让内核可以同时服务 CLI 批量质检、浏览器端交互校验和后续的服务端集成，而不产生逻辑分叉。

## 核心功能范围

- **STEP 文本解析**：支持 HEADER / DATA 区段识别、实体编号、字符串（含转义）、整数、浮点数、布尔值、枚举、实体引用、嵌套聚合以及 `$` / `*` 缺省值，并保留每个实体的源码行列位置；
- **解析诊断**：对重复实体编号、格式非法的实体、缺失分隔符、聚合括号未闭合和语句未终止等情况产生带位置的结构化错误，且多次解析结果顺序稳定；
- **领域实体建模**：识别 `IFCPROJECT`、`IFCSITE`、`IFCBUILDING`、`IFCBUILDINGSTOREY`、`IFCSPACE`、`IFCWALL`、`IFCDOOR`、`IFCWINDOW`、`IFCRELAGGREGATES`、`IFCRELCONTAINEDINSPATIALSTRUCTURE`、`IFCRELDEFINESBYPROPERTIES`，并归入项目、空间、构件、关系四类；未识别类型保留为实体并完整保留其原始属性与引用，不丢失信息；
- **GlobalId 提取**：仅对已识别类型从第一个字符串属性提取 `GlobalId`，避免把后续属性中的名称误判为标识符；
- **引用关系索引**：为实体编号、实体类型和双向引用建立索引，实现 `children_of` / `parent_of` 关系查询；嵌套聚合中的实体引用按首次出现顺序去重，同一实体被多个关系指定父级时返回首个父级；
- **审计规则调度**：以稳定顺序运行内置规则并输出结构化发现，每条发现包含规则编号、严重级别、来源实体编号与类型、源码位置、目标编号、说明和修复建议；
- **内置规则 `REF001`**：报告指向不存在实体的悬空引用，生成 `Error` 级别发现；合法的前向引用、自引用与循环引用不误报；未知实体类型同样参与引用检查；
- **内置规则 `GID001`**：报告重复的非空 `GlobalId`，首次出现的实体作为原始占用者，后续重复者各产生一条指向原始占用者的发现；比较区分大小写，缺失值、空字符串与未支持实体的首个字符串属性不参与检查；
- **稳定的结果排序**：同一来源实体对同一目标的重复引用只报告一次，不同来源分别报告；最终结果按 `REF001`、`GID001` 规则顺序、规则内部按源文件顺序稳定输出，天然适合作为 CI 门禁与差异对比基线；
- **三类报告输出**：`report_view` 提供 JSON、文本与引用列表三种视图，公共入口为 `json(AuditReport)`、`text(AuditReport)` 和 `tree(RelationMap)`；
- **多目标构建**：内核不依赖平台 API，同一份代码可编译到 wasm-gc、wasm、js 和 native，`moon.mod` 声明首选目标为 wasm-gc；
- **应用入口**：`apps/inspect_cli` 提供命令行入口，支持读取 `.ifc` 文件、`--text` / `--json` / `--tree` 三种视图切换、`--help` 用法说明，并在无参数时审计内置示例模型；`apps/browser_demo` 提供可编译到 WASM / JS 的最小入口与免前端依赖的演示页面；
- **STEP 解析诊断呈现**：CLI 在审计报告之外单独输出解析诊断（位置与说明），避免畸形 STEP 输入被静默忽略；退出码区分"无发现""有发现""存在解析诊断或读取错误"；
- **示例与文档**：`examples/` 提供正常模型与缺陷模型样本，`docs/` 记录架构设计、实体支持清单、已知限制与 Demo 说明；
- **持续集成**：GitHub Actions 流水线在全部包上执行格式化检查、跨目标检查与测试、四目标构建，并校验 `pkg.generated.mbti` 接口未发生非预期变更。

## 预期验收产物

- **`Mitsuha11zz/moonifc_inspector` MoonBit 库**：可通过 `moon add Mitsuha11zz/moonifc_inspector` 引入，或通过 `moon run apps/inspect_cli -- <文件.ifc>` 在命令行审计实际模型文件；
- **零平台依赖的解析与审计内核**：在 wasm-gc、wasm、js、native 四个目标上均可构建，`moon.mod` 首选目标为 wasm-gc，浏览器端无需任何服务端配合即可完成模型结构校验（文件读取能力由 CLI 侧的 `moonbitlang/x` 依赖提供，内核包本身仍不依赖任何平台 API）；
- **稳定的公开 API 契约**：核心入口为四段式流水线 `@step_text.parse(String) -> Document`、`@ifc_entities.build(Document) -> Array[Entity]`、`@relation_map.build(Array[Entity]) -> RelationMap`、`@model_rules.audit(RelationMap) -> AuditReport`，报告输出为 `@report_view.json(AuditReport)`、`@report_view.text(AuditReport)` 与 `@report_view.tree(RelationMap)`；关系查询提供 `RelationMap::children_of`、`parent_of`、`incoming_references`、`outgoing_references`、`entity_by_id`、`entities_by_type`；包接口以 `moon info` 生成的 `pkg.generated.mbti` 固化，并由 CI 校验其差异；
- **两个内置审计规则**：`REF001` 悬空引用检查与 `GID001` 重复 GlobalId 检查，输出的 `Finding` 结构包含规则编号、严重级别、来源实体编号与类型、源码行列位置、目标编号、说明与修复建议字段，结果顺序稳定可复现；
- **可扩展的规则调度接口**：新增审计规则无需改动解析层与应用层，规则以注册方式接入并保持既定输出顺序；
- **测试套件**：覆盖 5 个领域包与 2 个应用包；此前实测在 wasm、wasm-gc、js、native 四个目标上均为 23 通过、0 失败，现新增 `report_view` 包测试，最终数字以重跑结果为准；
- **三类报告视图**：JSON、文本与引用列表输出。JSON 视图序列化统计信息（实体数、类型数、引用数）及每条发现的 `code`、`severity`、`entity_id`、`entity_type`、`target_id`、`location`（行、列、偏移量对象，缺失时为 `null`）、`message`、`suggestion`；文本视图前几行为统计信息，随后每条发现输出为单行；引用列表视图按源文件顺序逐行输出实体编号、类型及其直接引用目标；
- **示例模型**：`examples/tiny-building.ifc` 与 `examples/broken-references.ifc` 提供正常路径与缺陷检出样本，可通过 CLI 以文件参数方式审计；
- **文档集**：`README.md` 快速开始与报告输出说明、`docs/architecture.md` 分层设计、`docs/supported-ifc.md` 支持范围与规则语义、`docs/demo.md` 演示说明；
- **WASM 浏览器端集成**（在研）：当前 `apps/browser_demo` 为可编译的 WASM / JS 最小入口，演示页面为文件选择占位实现，尚待接入 WASM 绑定与结果渲染。注意 `moonbitlang/x/fs` 在浏览器环境不可用（wasm 侧依赖 `moonrun` 主机函数、js 侧依赖 `node:fs`），浏览器端读文件需走 Web API 另行实现；
- **扩展审计规则**（规划）：空间归属校验、根实体唯一性校验、必需属性缺失校验，以及 STEP 解析错误与审计发现的合并呈现；
- **完整 EXPRESS 类型系统**（规划）：按 IFC 模式定义自动派生实体属性槽位，替代当前基于目录表的手工分类；
- **压缩 IFC（ifcZIP）与几何解析**（暂不纳入范围）：三维渲染与几何求交明确不属于本项目目标，保持解析内核的轻量定位。

## 移植或参考说明

- 原项目名称：无（本项目为原创实现，非移植项目）
- 原始规范名称：IFC（Industry Foundation Classes）第 4 版，ISO 16739-1
- 原始规范发布方：buildingSMART International
- 原始规范链接：https://standards.buildingsmart.org/IFC/RELEASE/IFC4/ADD2_TC1/HTML/
- 物理文件格式规范：STEP Part 21（ISO 10303-21）
- 原始规范许可证：IFC 规范本身未采用开源软件许可证，由 buildingSMART 以公开标准形式发布，允许自由实现
- 本项目许可证：Apache-2.0

本项目不复制、不移植任何现有实现代码，而是依据公开的 IFC4 与 ISO 10303-21 规范，在 MoonBit 中独立实现解析与审计能力。作为格式与语义的对照参考，业界存在 IfcOpenShell、xBIM、ifc.js 等实现，本项目与它们在代码层面无任何派生关系。与原规范及上述参考实现相比，本项目会做以下简化和重新设计：

- 使用 MoonBit 原生包结构、类型系统和测试方式组织代码，而不是复刻 C++ / .NET / JS 的既有工程结构；
- 首版聚焦建筑模型结构性缺陷检出，明确剥离几何运算、三维渲染与拓扑求交，把能力边界收敛到"解析 + 审计"这条链路；
- 以 WASM 为核心交付形态，解析器不依赖任何平台 API，避免为跨平台适配引入条件编译分支；
- 对未识别的实体类型采取"保留原始数据而非丢弃"的保守策略，保证信息不丢失，为后续扩展留出空间；
- 对完整 EXPRESS 类型系统、压缩 IFC、空间语义校验等当前未实现的能力明确标注为范围之外，并在文档中如实记录已知限制，不以"已支持"表述覆盖未完成部分；
- 以 MoonBit API 与 JSON 报告为主要交付接口，方便接入 Web、CLI 与可视化渲染场景。
